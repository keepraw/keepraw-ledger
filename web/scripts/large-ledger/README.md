# Large ledger reliability and performance suite

All fixtures are fictional. `storage-benchmark/fixture.mjs` is the unchanged
PR #26 generator (seed 1263684657). Install the repository's locked dependencies
with `cd web && npm ci`; no additional production dependency is needed.

Run from the repository root with Node 22+ and Chromium:

```sh
LEDGER_MODE=backup LEDGER_FRESH_PROFILES=3 node web/scripts/large-ledger/run.mjs
LEDGER_MODE=performance node web/scripts/large-ledger/run.mjs
LEDGER_MODE=migration node web/scripts/large-ledger/run.mjs
LEDGER_MODE=index node web/scripts/large-ledger/run.mjs
```

`CHROMIUM_PATH` defaults to `/usr/bin/chromium`. Override `LEDGER_SIZES` for a
short smoke test (for example `100`) or a selected scale. Backup defaults to
18k/36k/100k; performance, migration and index default to 18k/100k. `LEDGER_OUTPUT`
selects the JSON results path. `LEDGER_WEB_ROOT` builds another checkout with
exactly the same probe, fixture generator and dependencies for a before/after
comparison. Supplemental `read` mode requires `LEDGER_PROFILE_ROOT` and
`LEDGER_ORIGIN_PORT` from a completed synthetic performance result. It uses
those three generated profiles for 3 warm reads plus 7 measured reads each.
Probe navigation disables HTTP cache and uses a fresh query string to avoid
restoring an outdated probe; this happens outside the read timing. This mode
does not replace the mixed-workload benchmark. Use only generated synthetic
profiles. The supplemental `read` mode requires `LEDGER_PROFILE_ROOT` and
`LEDGER_ORIGIN_PORT` from a completed synthetic performance result, and reuses
those three profiles for 3 warm reads plus 7 measured reads each. It disables
HTTP cache during probe navigation so a reused profile cannot load an old probe;
this setup happens outside the database read timing. It does not replace the
primary mixed-workload benchmark. Use only profiles generated by this suite. Run benchmark modes sequentially on an otherwise idle machine.

The runner builds the real application and a separate probe with Vite in
production mode, serves only local compiled assets and fictional fixtures, and
blocks browser requests to other origins. Each case uses a fresh persistent
Chromium profile. Profiles and synthetic data remain under the printed temporary
directory for inspection. `LEDGER_TEMP_DIR` overrides the system temporary root. Temporary generated source files are removed on exit.
The suite uses the TypeScript history importer and normal AppProvider
persistence. Large migrations additionally seed full importer-generated objects
into historical Dexie v1/v2 schemas, or the v3 index structure for controlled
write/storage comparisons. This direct seed path is recorded separately.

Backup mode exports actual V2 JSON/ZIP downloads (with a realistic distribution of
independent free-text notes seeded every 20th transaction), checks newer local
edits survive restoring older exports, verifies conflicting note content rejects
without partial changes, clears the synthetic ledger, restores into new profiles
and repeats restoration. Every transaction field, note content/timestamp and the
statements/imports are compared in the browser. Original attachment metadata and
SHA-256 bytes are checked, and a native 100k restore is forced to fail at the
late attachment write to prove cross-store rollback (transactions, notes and
attachments all roll back). Legacy pretty JSON, old format identifiers, partial
settings and nonstreaming STORE ZIPs are exercised. V2 fresh profiles recover
all notes; legacy V1 payloads (stripped `reviewNotes`, `version: 1`) preserve
existing notes while fresh V1 profiles invent none. A fresh ZIP restores the
original bytes and contract metadata; its attachment `importedAt` is
reconstructed by the existing restore contract. Existing restores and migrations
require stored timestamps (including note `updatedAt`) to remain exact.

Performance mode runs three independent XLSX imports, three page-ready samples,
five read/refresh/filter/sort/edit samples and three actual JSON downloads. React
commit uses a layout effect; UI samples measure captured input/click through two
animation frames. The original pretty-JSON encoding microbenchmark remains
separate from the actual download API. Dates and descriptions use the production
sorter where present, with the exact original comparator for old main.

Migration mode now verifies v1/v2/v3 -> v4, failed v2 upgrades, new v4 stores, three
reopens, and every stored field including notes, original timestamps/bytes and
settings. Native IndexedDB version numbers are 10/20/30/40 for Dexie v1/v2/v3/v4. Historical v2
and v3 controls have three separately seeded profiles each for write/storage medians.
Queries and edits are sampled three times per profile. Index mode compares v2/v3
without upgrading the old controls, then shuts down and reopens both schemas
read-only before recording their stable storage estimates and file sizes.

JSON sizes are UTF-8 bytes. `navigator.storage.estimate()` covers the entire
origin and is an estimate. Physical file sizes sum only `Default/IndexedDB`
files in the isolated profile; allocated bytes use `stat.blocks * 512`. Physical
measurements include LevelDB logs, retained obsolete entries and filesystem
allocation; they are not exact index sizes or a compaction guarantee. Before
measurements occur after seeding and the read/write samples; after measurements
occur after browser shutdown. Fresh schema comparisons use the same checkpoints.
Backup-only memory sampling sums owned Chromium process RSS through CDP + `ps`;
shared pages can be counted more than once. It is not a hard JS heap limit.
Memory sampling is disabled during the performance comparisons.

Small financial, state-race and schema-abort regressions run in ordinary Vitest
and Playwright suites. The full 100k suite is deliberately a separate command.

`read-native` uses the same reuse configuration to alternate ordinary Dexie
reads with a test-only native readonly getAll implementation (7 pairs per
profile). It verifies complete snapshots match after sampling. It is an
experiment, not a production path or a replacement for the main benchmark.

The active probes no longer read or measure an independent `merchant` transaction
field. Archived v2/v3 storage results retain their original schema and measurements;
they are not v4 performance evidence. Ordinary Chromium tests separately exercise
v3 records carrying the retired field and rollback after the real v4 deletion.
