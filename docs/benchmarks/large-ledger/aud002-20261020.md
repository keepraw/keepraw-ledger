## Baseline and environment

Remote main was rechecked at `2c6d42c45ceb2da3866af9cffe6bae1fc529cc41`.
[Validation](https://github.com/keepraw/keepraw-ledger/actions/runs/39359404713)
(web and deploy) and [Commit identity](https://github.com/keepraw/keepraw-ledger/actions/runs/39359404719)
succeeded. Pages deployment `7190041851` succeeded for that SHA. The initial
`work` branch was clean, had no local commits ahead of main, and no unpublished
user changes were discarded. Work uses `fix/aud002-large-ledger-performance`.

Measurements use Debian 13, Linux 6.18.55 x64, AMD EPYC 9V45, five visible CPUs,
four-core cgroup quota, 16 GiB cgroup memory limit (host reports 18,882,674,688
bytes), Node v24.19.0, npm 11.9.0, system Chromium 154.0.8037.57, zh-CN browser
locale, UTC browser time, 1440x1000 viewport. These are same-host comparisons;
old `before.json`, `after.json`, `after-sort-first.json` and the historical 399/
487 ms measurements are not this baseline.

The runner imports `scripts/storage-benchmark/fixture.mjs`; there is no
`large-ledger/fixture.mjs` at this HEAD. The seed is `0x4b524c31` (1263684657).
Invented data covers six banks, 2018–2025 dates, five currencies, approximately
1% deliberately repeated purchases and mixed credit/debit transaction types.
Only generated profiles/databases are used. No real data is opened or modified.

The first attempt completed 18k but 100k correctly hit AUD-014's 25 MiB/file
limit. `aud002-20261020-oversize-attempt.json` preserves that attempt's 18k
measurements. The harness now imports the same 100k rows as two 50k workbooks
through the normal production preview/confirm API; it asserts every valid-row
count and exactly 100,000 persisted transactions. There are still three complete
fresh-profile import cycles per size, five calculation/edit/UI samples, three
actual JSON backups and three new-page startups. Import timings sum all parts;
they must not be compared with historical one-file import timings. The normal
18k workbook is unchanged in scope. Both accepted campaigns use this same harness.

Existing timing segments are retained. Metadata adds browser/OS/sample counts,
and a separate `searchAllMs` measures unbounded text search (the original
`filteredSearchMs` includes bank/date filtering). Browser interaction is event
capture through two animation frames; startup is navigation through the first
observed full-count heading on a new page in the same profile. These are neither
cold-browser startup nor an INP measurement. `readMs` includes coherent IndexedDB
reads and object materialization; it does not isolate storage IO from decoding.

## Predeclared budgets

Budgets below were set after the accepted baseline and before production edits.
They apply to medians on this machine, with all samples/ranges retained in raw
JSON. Absolute millisecond checks belong to this controlled benchmark, not noisy
shared CI. The deterministic collation-comparison test is the CI guard.

| Metric (ms) | 18k budget | 100k budget | Reason |
| --- | ---: | ---: | --- |
| Full snapshot read | 150 | 750 | Guard unchanged IO/materialization |
| Full filter | 4 | 20 | Guard full-ledger scan |
| Full text search | 6 | 45 | Guard unchanged text matching |
| Bank/date-filtered search | 4 | 25 | Guard combined filtering |
| Date sort computation | 20 | 140 | Guard dedicated date comparator |
| Description sort computation | 15 | 120 | Reduce measured repeated collation cost |
| Search input through paint | 50 | 100 | Keep current responsive search |
| Date sort click through paint | 50 | 160 | Guard full-order UI path |
| Description sort click through paint | 45 | 160 | Improve the measured bottleneck |
| Edit commit / paint | 50 / 60 | 160 / 180 | Keep incremental state updates |
| Refresh through paint | 180 | 1000 | Guard coherent snapshot replacement |
| New-page transaction startup | 400 | 1200 | Guard full-count page readiness |

Before production changes, `transactionsPerformance.test.tsx` fails with
**91,376 collation calls**, against a budget of **less than 512**, for 18,000 rows
and 32 distinct descriptions. The other seven new/existing targeted cases pass.
The assertion is about expensive work, not hardware speed, and the expected
ordering is independently produced by the original comparator.

## Reproduction

```sh
cd web
npm ci --cache /workspace/.npm-cache
LEDGER_MODE=performance LEDGER_SIZES=18000,100000 \
  CHROMIUM_PATH=/usr/bin/chromium \
  LEDGER_OUTPUT="$PWD/../docs/benchmarks/large-ledger/aud002-20261020-before.json" \
  LEDGER_TEMP_DIR="$PWD/../work/aud002" node scripts/large-ledger/run.mjs
```

Use `-after.json` for the optimized run; never overwrite historical evidence.
The first baseline command ran against production source at the main SHA with
only measurement/test additions in the worktree. Raw JSON records production
source hashes to identify that distinction from later commits. A first `npm ci`
attempt failed because the default home cache was unwritable; the explicit
workspace cache completed a clean locked install without dependency changes.

Results, implementation details and complete validation are appended after the
same-environment optimized campaign.
